## 1. 채택 방법론: 적응형 마일스톤 개발 (AMD)

### 방법론 선정 근거

| 대안 | 탈락 이유 |
|------|---------|
| 스크럼 | 1인 개발 — 스탠드업·스프린트 회고 등 팀 세레모니 불필요, 오버헤드만 발생 |
| 폭포수 | 각 Phase 내부에서 임계값 튜닝·재테스트 반복이 필요 — 순수 폭포수 부적합 |
| 순수 칸반 | 마감(8/27) 대비 진척 가시성 낮음, 완료 기준 없이 흘러갈 위험 |
| XP/TDD | 인프라 계층(Docker, Logstash) 전체 적용 불가 — 선택적 TDD로 대체 |

**AMD 선택 이유:**
- v4 계획서의 6단계 일정이 AMD 마일스톤 구조와 1:1 대응
- 인프라 의존성 체인(ELK → Faker → Rules → LLM → Kibana)에 선형 Phase 구조 적합
- 정량 측정(evaluate.py)이 가능해 Phase-Gate 기준 설정 가능
- 1인 개발이므로 세레모니 최소화

### AMD 핵심 원칙

1. **Phase-Gate**: 각 Phase DoD(완료 기준) 100% 충족 시에만 다음 Phase 진입
2. **스파이크 우선**: 새 통합 포인트마다 최대 2일 PoC → 실패 시 즉시 대안 전환
3. **측정 게이트**: Phase 3 완료 시 `evaluate.py`로 Recall·FP율 측정 후 결과를 README 공개 (목표 수치 없음 — 재현 가능한 측정 방법 자체가 기여)
4. **Ollama 독립성 원칙**: LLM 오프라인 시에도 탐지·알림 정상 동작. 모든 모듈은 Ollama 없이 테스트 가능

## 2. 개발 원칙

- **설정값 외부화**: 탐지 임계값(횟수·금액·시간) 전부 `config/config.yaml`로 분리
- **재현 가능성**: `docker compose up` 한 명령으로 전체 스택 실행 가능한 상태 유지
- **린 칸반**: GitHub Issues 4열(Backlog / In Progress / Done / Blocked)로 진행 추적
- **브랜치 전략**: `main` 항상 실행 가능 상태 유지, 기능 개발은 `feature/*` 브랜치
- **코드 이해 원칙**: AI 보조 도구(Claude 등)로 작성된 코드는 반드시 동작 원리를 직접 이해하고 검증한 후 커밋 (대회 규정 제9조⑤ — 이해도 부족 시 감점)

## 4. 테스트 전략: 선택적 TDD

인프라(Docker, Logstash, Kibana)는 설정 파일이라 "테스트 먼저 작성"이 불가능하다. 모듈별로 전략을 다르게 적용한다.

### 모듈별 테스트 전략

| 모듈 | 전략 | 이유 |
|------|------|------|
| `engine/rules/*.py` | **TDD** | 순수 Python 로직, 입출력 결정적 → 테스트 먼저 작성 후 구현 |
| `evaluate.py` | **TDD** | 수학 계산(TP/FP/FN 집계) → 테스트로 명세 확정 후 구현 |
| `api/routers/*.py` | **TDD** | FastAPI `TestClient`로 HTTP 레벨 단위 테스트 가능 |
| `engine/llm/chain.py` | **Mock 테스트** | Ollama 응답 비결정적 → `unittest.mock`으로 대체 |
| `engine/alerting/slack.py` | **Mock 테스트** | 외부 Webhook → mock으로 호출 여부만 검증 |
| `engine/alerting/email.py` | **Mock 테스트** | Gmail SMTP → mock으로 전송 호출 여부만 검증 |
| `data_gen/*.py` | **형식 검증** | 생성 로그의 필드·타입 존재 여부 확인 |
| Docker / Logstash / Kibana | **스모크 테스트** | 설정 파일 — `docker compose up` 후 직접 확인 |

### TDD 사이클 (룰 엔진 기준)

1. `test_rules.py`에 실패하는 테스트 먼저 작성 — 탐지 케이스(공격 패턴 → Alert 반환)와 정상 케이스(정상 트래픽 → 빈 리스트) 각각 명세
2. 룰 구현 (테스트를 통과할 만큼만)
3. `pytest` 통과 확인
4. 리팩터링 (`config.yaml` 임계값 외부화, `base.py` 인터페이스 정리)
5. 다음 룰로 반복

### Ollama Mock 전략

`chain.py`는 `unittest.mock.patch`로 Ollama 호출을 대체한다. 정상 응답 케이스와 `ConnectionError` 케이스 두 가지를 테스트하여, 오프라인 시 `null` 저장 정책이 실제로 동작함을 검증한다.

### conftest.py 역할

- `sample_logs`: 룰 테스트용 공통 로그 픽스처 (정상·공격 혼합)
- `mock_slack`: Slack Webhook 호출 차단 픽스처 — 테스트 중 실제 알림 발송 방지
- `mock_email`: Gmail SMTP 전송 차단 픽스처 — 테스트 중 실제 이메일 발송 방지

### CI 자동 실행

`pytest`는 GitHub Actions로 `feature/*` → `main` PR 시 자동 실행한다.  
인프라 의존성 없는 단위·mock 테스트만 CI에 포함하고, 통합 테스트는 로컬에서 수동 실행한다.
