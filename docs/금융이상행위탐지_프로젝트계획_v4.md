## 3. 핵심 기능

### 탐지 룰셋 (금감원·금보원 FDS 운영 가이드라인 기반)

금융감독원·금융보안원이 2023년 10월 발표하고 2024년 1월부터 시행 중인 「이상금융거래탐지시스템(FDS) 운영 가이드라인」의 공동 이상거래탐지룰(51개)을 참고하여 아래 룰셋을 구현한다.

| 탐지 유형 | FDS 가이드라인 근거 | 탐지 기준 | 수치 출처 |
|-----------|---------------------|-----------|-----------|
| 크리덴셜 스터핑 | FDS 가이드라인 — 비정상 로그인 시도 탐지 시나리오 | 동일 IP에서 10분 내 10개 이상 계정 로그인 시도 | 구현 시 설정값 (조정 가능) |
| 새벽 고액 이체 | FDS 가이드라인 — 비정상 시간대 고액 이체 시나리오 | 00:00~05:00 사이 300만원 이상 이체 요청 | 구현 시 설정값 (조정 가능) |
| 다중 계정 접근 | FDS 가이드라인 — 단일 기기 다중 계정 접근 시나리오 | 단일 IP에서 30분 내 4개 이상 계정 접근 | 구현 시 설정값 (조정 가능) |
| 비정상 User-Agent | FDS 가이드라인 — 자동화 도구 접근 탐지 시나리오 | 자동화 스크립트 UA(python-requests, curl 등) 탐지 | 구현 시 설정값 (조정 가능) |
| 분할 이체 | FDS 가이드라인 — 한도 회피 소액 반복 이체 시나리오 | 동일 계정에서 1시간 내 한도 직전 금액 5회 이상 반복 | 구현 시 설정값 (조정 가능) |

> FDS 운영 가이드라인 적용 범위: '로그인 → 전자금융거래 → 로그아웃' 전 단계. 각 룰셋은 가이드라인 시나리오와 1:1 매핑하여 문서화 예정.
> 탐지 수치(시간·횟수·금액)는 FDS 가이드라인 원문에서 공개된 구체적 수치가 없어 구현 시 설정값으로 지정하며, 실제 운영 환경에 맞게 조정 가능하도록 설계.

### LLM 자동 분석 (방어적 관점)

탐지 이벤트 발생 시 LangChain LCEL 체인을 통해 Ollama (llama3.1:8b)로 다음을 자동 생성:

- **Root Cause** — 이상 행위의 근본 원인 분석
- **위협 시나리오** — 해당 패턴이 어떤 공격에 해당하는지 (방어적 서술)
- **Countermeasure** — 즉시 적용 가능한 대응 방안

> LangGraph 미사용 이유: 현재 분석 흐름이 탐지 이벤트 → 프롬프트 → 결과 반환의 선형 파이프라인이므로 LangChain LCEL 체인으로 충분. LangGraph는 멀티에이전트·조건 분기가 필요한 고도화 단계에서 도입 검토.

**Ollama 장애 처리 정책:**
- Ollama 오프라인 시에도 룰셋 탐지 결과는 Elasticsearch에 저장되고 Slack 알림·이메일 알림은 정상 발송
- LLM 분석 결과는 `null`로 저장되며 대시보드에 "AI 분석 불가 (Ollama 오프라인)" 표시
- 즉, LLM은 부가 기능이며 탐지·알림 핵심 기능은 Ollama와 독립적으로 동작

### 대시보드 & 알림

- 준실시간 거래 로그 모니터링 대시보드 (Logstash polling_interval: 5s, 수 초 이내 반영)
- 위험도별 분류 (위험 / 경고 / 정상)
- Slack Webhook 알림 + Gmail SMTP 이메일 알림 (무료 — Gmail 앱 비밀번호 + Python `smtplib` 내장 모듈, 추가 패키지 없음)

## 4. 기술 스택

```
Frontend        Kibana (ELK 내장 대시보드, 별도 개발 불필요)
Backend         FastAPI (Python) — 탐지 엔진 + LLM 연동
로그 파이프라인   Logstash → Elasticsearch (polling_interval: 5s)
AI 분석         LangChain LCEL + Ollama (llama3.1:8b Q4, 로컬 실행)
데이터          Faker 기반 금융 웹 로그 생성기 (자체 제작)
배포            Docker Compose (Ollama 제외한 나머지 스택)
```

> **배포 구조:** ELK + FastAPI + Kibana는 Docker Compose로 단일 명령 실행. Ollama는 데스크탑(RTX 4060 Ti)에서 별도 실행 후 FastAPI가 로컬 네트워크로 호출하는 구조.

### LLM 선택 근거 (Ollama 로컬 실행)

| 항목 | 내용 |
|------|------|
| 모델 | llama3.1:8b (Q4 양자화, 약 4.7GB) |
| 실행 환경 | 데스크탑 GPU (RTX 4060 Ti 8GB VRAM) |
| VRAM 사용량 | 약 6GB (2GB 여유) |
| 선택 이유 | 금융 로그 데이터를 외부 API로 전송하지 않아 보안상 안전 / 온프레미스 배포 가능 / 완전 무료 |
| 개발 방법 | 데스크탑에서 Ollama 서버 실행 (`OLLAMA_HOST=0.0.0.0`), 노트북에서 API 호출 |

> Next.js 프론트 개발은 MVP 범위에서 제외. Kibana로 대시보드를 구성하고 룰셋·LLM 파이프라인 완성도에 집중.

## 5. 데이터 전략

실제 금융 데이터 대신 자체 제작한 로그 생성기 활용:

| 소스 | 설명 | 활용 목적 |
|------|------|----------|
| **Faker 기반 로그 생성기** | 금융 API 서버 웹로그(IP, UA, endpoint, amount 등) 가상 생성 | 정상 트래픽 + 공격 패턴 혼합 환경 구성 |
| **공격 시나리오 주입기** | 크리덴셜 스터핑 / 새벽 이체 / 분할 이체 등 패턴별 로그 생성 | 탐지 룰셋 정확도 검증 |

> PaySim 미사용 이유: PaySim은 거래 원장 데이터(IP·UA 필드 없음)로 웹 서버 로그 기반 탐지 룰과 구조 불일치

### 성능 지표 (KPI)

로그 생성 시 `label` 필드(normal / attack)를 포함하여 `evaluate.py`로 자동 측정:

| 지표 | 측정 방법 |
|------|----------|
| 탐지율 (Recall) | `evaluate.py` 자동 계산 → 결과를 README에 투명하게 공개 |
| False Positive율 | `evaluate.py` 자동 계산 → 결과를 README에 투명하게 공개 |

> **목표 수치를 명시하지 않는 이유:** 로그 생성 데이터와 탐지 룰을 동일 설계자가 만들기 때문에 어떤 수치든 신뢰하기 어렵다. 재현 가능한 측정 방법(`evaluate.py`)과 데이터셋 설계(정상 9,500건 + 공격 500건)를 공개하는 것이 더 신뢰를 준다.
>
> `evaluate.py`: 로그 생성 → 탐지 엔진 실행 → label 기반 Recall·FP율 자동 계산·출력. MVP 일정(7월 하순)에 포함하여 수상작 검증 시 측정 결과 재현 가능하도록 구성.
